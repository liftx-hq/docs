## Authorization and query

The owning integration namespace can read its receipt with any valid key. Alternatively, a key with `read` can inspect a **known receipt UUID from the same account** when its link/instrument policy permits that receipt. This enables an API controller to inspect a TradingView receipt without acquiring that TradingView namespace's mutation identity or list access.

| Query field | Requirement | Meaning |
| --- | --- | --- |
| `id` | Required | Canonical lowercase, nonzero receipt UUID. This is not `client_command_id` and is not an arbitrary position UUID. |

Send exactly one `id`, no other query keys and no request body.

```sh
curl --fail-with-body --get \
  -H "Authorization: Bearer ${LIFTX_API_KEY}" \
  --data-urlencode 'id=33333333-3333-4333-8333-333333333333' \
  https://api.liftx.io/v1/commands/get
```

## Single-command response: HTTP 200

```json
{
  "id": "33333333-3333-4333-8333-333333333333",
  "client_command_id": "btc-controller:cycle-001:terminate",
  "action": "terminate",
  "state": "handed_off",
  "position_id": "11111111-1111-4111-8111-111111111111",
  "error_code": null,
  "created_at": 1893456120,
  "updated_at": 1893456121,
  "terminal_request_kind": 1,
  "terminal_request_seq": 2
}
```
The synthetic example records a durably armed close (`terminal_request_kind:1`, positive sequence `2`). It does not certify completed closure. A canceled pending lifecycle can instead record kind `2`; a receipt without newly correlated terminal evidence omits those two optional fields.

### Receipt fields

| Field | Presence | Meaning |
| --- | --- | --- |
| `id` | Always | Server receipt UUID. |
| `client_command_id` | Always | Original immutable client identity, or reserved server identity for a group child. |
| `action`, `state` | Always | Command action and current receipt state. |
| `position_id` | Always, nullable | Exact target for a single command/child; `null` for a group parent. |
| `error_code` | Always, nullable | Machine-readable outcome code; inspect even when this GET returned HTTP `200`. |
| `created_at`, `updated_at` | Always | UTC Unix seconds. These are command timestamps, not exchange fill timestamps. |
| `terminal_request_kind`, `terminal_request_seq` | Only when correlated evidence exists | Durable terminal arm kind (`1` close, `2` cancel) and positive sequence. They may be visible during `dispatching`. |
| `group_id` | Group children only | Parent receipt UUID. |
| `group` | Group parents only | Frozen target selector/count and child state counts. |
| `targets` | Nonempty group detail | Up to 64 exact child receipts. A zero-target group can omit this field. |

See the [state table](/api/commands-and-receipts#receipt-states). Receipt GET success means the read succeeded; it does not turn `rejected`, `expired` or `operator_required` into a successful trade.

`partial` is a resolved group summary with mixed child outcomes. For a group with unresolved children, the summary instead reflects `operator_required`, then `dispatching`, then `accepted` in priority order. A zero-target group is `execution_observed` with `target_count:0`, all counts zero and no required `targets` array.

The target set was frozen at admission. Retrying a group does not add later positions or execute finished children again. A successful child handoff still needs position-level completion checks. A null parent `error_code` does not conceal the rejected child's code; inspect every child.

## Unresolved execution example

A receipt read can return HTTP `200` with:

```json
{
  "id": "22222222-2222-4222-8222-222222222222",
  "client_command_id": "btc-controller:cycle-001:modify-001",
  "action": "modify",
  "state": "operator_required",
  "position_id": "11111111-1111-4111-8111-111111111111",
  "error_code": "EXECUTION_UNCERTAIN",
  "created_at": 1893456060,
  "updated_at": 1893456062
}
```
Stop dependent mutations and reconcile the existing lifecycle. The available evidence does not justify a fresh command that repeats or compensates for the unresolved one.

## Read errors

Malformed or missing `id` produces HTTP `400`:

```json
{
  "success": false,
  "error": {
    "code": "INVALID_ID",
    "message": "Canonical receipt ID required"
  }
}
```
A receipt absent from the authorized result, including one no longer retained, returns HTTP `404`:

```json
{
  "success": false,
  "error": {
    "code": "NOT_FOUND",
    "message": "Receipt not found"
  }
}
```
Do not infer that a historical command never executed from a later `404`. Resolved receipt retention is finite; retain your own audit evidence. Use [namespace history](/api/reference/get-v1-commands) when recovering a lost response without a known receipt UUID, or retry the exact saved command while its receipt remains retained.
