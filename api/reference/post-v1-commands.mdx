<Note>Examples are illustrative; the documentation cannot submit requests.</Note>

Submit one immutable intent using a scoped API key. Liftx persists the intent before an existing trading owner executes it. A new command returns `202 Accepted`; an identical retry returns `200 OK` with the current receipt for the original command.

## Headers and request rules

```http
POST /v1/commands HTTP/1.1
Host: api.liftx.io
Authorization: Bearer YOUR_API_KEY_FROM_PRIVATE_STORAGE
Content-Type: application/json
```

Use `positions:open`, `positions:modify` or `positions:terminate` for the corresponding action. Pro or an eligible trial is required. This endpoint accepts one JSON object up to 256 KiB, with exact case-sensitive field names and no duplicate or unknown keys. Compressed bodies are unsupported. Decimal coefficients are strings; do not convert money through binary floating-point.

| Field | Required or conditional | Meaning |
| --- | --- | --- |
| `client_command_id` | Required for every command | Immutable identity within the integration namespace; 1-256 UTF-8 bytes; `liftx-group:` is reserved. |
| `issued_at` | Required | UTC Unix seconds. Unseen intent must be no more than 300 seconds old or 30 seconds ahead of the admission clock. |
| `expires_at` | Required | UTC Unix seconds, later than issuance and no more than 300 seconds later; must not have elapsed for a new command. |
| `action` | Required | Exactly `open`, `modify` or `terminate`. |
| `exchange_link_id`, `instrument_id` | Required | Exact authorized link and its catalog instrument. |
| `target` | Optional | Omit or use `position`. Strategy/market groups belong to the TradingView endpoint. |
| `position_id` | Required for MODIFY/TERMINATE; omit for OPEN | Canonical Liftx position UUID. |
| `expected_revision` | Required for API MODIFY | Positive revision from a fresh modification publication. It does not replace current row identities. |
| `request` | Required for OPEN/MODIFY; omit for TERMINATE | Complete [PositionRequest](/api/position-request); inner link/instrument must equal the envelope. |

Omit TradingView-only fields (`client_position_id`, `position_started_at`, `source_instance_id`, `sequence`, `binding_revision`) from API commands. Optional inactive fields do not need placeholder values. `request:null` is not a TERMINATE request.

## OPEN: limit entry with SL, SLx and TP

All examples on this page use a fictitious account link `17`, illustrative UUIDs and `2030-01-01` UTC timestamps. `BTC-USDT-SWAP` illustrates an exact canonical catalog ID for a supported BTC/USDT linear perpetual; it is not a universal symbol alias. Assume the selected catalog permits the depicted order roles, cross margin, 2x leverage, price ticks and `0.001 BTC` quantity. Resolve your own link and current catalog first. These values are not live quotes, minimum-size claims or trading recommendations.

This requests a long `0.001 BTC` limit entry at `70,000 USDT`, static SL at `68,600`, price-trigger trailing SLx, and a full-position virtual-limit TP at `72,100`. TP weight `1000000` means one full TP; its zero quantity placeholder is sized by the existing protection owner from actual exposure. See [OPEN](/api/open-positions) for market/spot differences and catalog sizing.

### New acceptance: HTTP 202

```json
{
  "id": "11111111-1111-4111-8111-111111111111",
  "client_command_id": "btc-controller:cycle-001:open",
  "action": "open",
  "state": "accepted",
  "position_id": "11111111-1111-4111-8111-111111111111",
  "error_code": null,
  "created_at": 1893456000,
  "updated_at": 1893456000
}
```
The current OPEN allocator uses the new command UUID as the position UUID, so these two fields match. Persist both returned fields instead of deriving one in client code. A position ID in an accepted receipt does not prove that the canonical position exists yet, that its order was placed or that it filled.

## TERMINATE: cancel pending work or close exposure

```json
{
  "client_command_id": "btc-controller:cycle-001:terminate",
  "issued_at": 1893456120,
  "expires_at": 1893456180,
  "action": "terminate",
  "exchange_link_id": 17,
  "instrument_id": "BTC-USDT-SWAP",
  "position_id": "11111111-1111-4111-8111-111111111111"
}
```
Do not send a position request, quantity or stale pending/open classification. The existing terminal owner reconciles fills, cancels pending work and closes remaining exposure as appropriate. A new acceptance is:

```json
{
  "id": "33333333-3333-4333-8333-333333333333",
  "client_command_id": "btc-controller:cycle-001:terminate",
  "action": "terminate",
  "state": "accepted",
  "position_id": "11111111-1111-4111-8111-111111111111",
  "error_code": null,
  "created_at": 1893456120,
  "updated_at": 1893456120
}
```
See [termination outcomes](/api/terminate-positions) for durable close/cancel receipts and the separate checks for completed closure.

## Admission errors versus execution outcomes

These are errors from this HTTP submission, with the exact integration error envelope.

HTTP `409 Conflict`, if a known client ID is reused with changed intent:

```json
{
  "success": false,
  "error": {
    "code": "COMMAND_CONFLICT",
    "message": "Command identity already belongs to a different payload"
  }
}
```
HTTP `400 Bad Request`, if API MODIFY omits the outer revision:

```json
{
  "success": false,
  "error": {
    "code": "REVISION_REQUIRED",
    "message": "Modification requires the current position revision"
  }
}
```
Other admission errors include `INVALID_JSON` (400), `SCOPE_MISMATCH` (400), `SCOPE_DENIED` (403), `STALE_COMMAND` (409), `PENDING_CAPACITY` (429), and `ADMISSION_UNAVAILABLE` (503). An acceptance commit whose result is unknown returns `ACCEPTANCE_UNCERTAIN` (503): retry the exact saved identity and payload, not a newly timestamped command.

After `202`, execution errors appear in the **receipt**, not in a second HTTP submission response. For example, an otherwise valid modification with no earlier effects can later be `rejected` with `POSITION_REVISION_CONFLICT`; uncertain side effects instead remain `operator_required`. A receipt GET still returns HTTP `200` for either state. See [receipt states and recovery](/api/commands-and-receipts).

## Submit a reviewed file

```sh
curl --fail-with-body \
  -H "Authorization: Bearer ${LIFTX_API_KEY}" \
  -H 'Content-Type: application/json' \
  --data-binary @reviewed-command.json \
  https://api.liftx.io/v1/commands
```

Create a current deadline only for a deliberately new intent. For a transport retry, retransmit the exact saved command. Identical known retries may return a later receipt state; they do not execute the mutation again. Use [receipt detail](/api/reference/get-v1-commands-get) for command progress and [position state](/api/position-state) or the [stream](/api/reference/get-v1-stream) for trading outcomes.
