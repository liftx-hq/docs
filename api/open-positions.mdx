---
title: "Open a position"
description: "Build catalog-sized market or limit entries with complete SL, SLx and TP configuration."
---

Use `positions:open` and [POST /v1/commands](/api/reference/post-v1-commands). Also grant `read` in the intended link/instrument scope when your controller needs catalog discovery and lifecycle reconciliation.

## Resolve the market before sizing

1. Select the exact account through `/v1/exchange-links` and the instrument through `/v1/symbols/list`.
2. Check product topology, trading state, tick/lot steps, minimum/maximum size, order roles and account configuration. Read fees and eligible settlement currency where applicable.
3. Express each quantity in `quantity_asset` units. For a linear product, BTC input is BTC, not a venue contract count. Quote input is quote notional, not margin collateral.
4. Build one complete [PositionRequest](/api/position-request), including protections that should belong to the lifecycle from creation.
5. Save a new command identity, issuance time, deadline and full request before sending it. Omit `position_id`; Liftx allocates it once for that accepted OPEN.

All examples on this page use a fictitious account link `17`, illustrative UUIDs and `2030-01-01` UTC timestamps. `BTC-USDT-SWAP` illustrates an exact canonical catalog ID for a supported BTC/USDT linear perpetual; it is not a universal symbol alias. Assume the selected catalog permits the depicted order roles, cross margin, 2x leverage, price ticks and `0.001 BTC` quantity. Resolve your own link and current catalog first. These values are not live quotes, minimum-size claims or trading recommendations.

The active configuration is:

| Part | Intent and applicable fields |
| --- | --- |
| Entry | `position_side:1` is long; `open_order_type:1` is limit. One row is `70,000 USDT` and `0.001 BTC`; `order_grid_enabled:false` needs no row count. |
| Derivative account | `margin_mode:1` is cross; `leverage:2` is 2x. Both require support from this exact account/instrument. |
| SL | Enabled, market-style exit (`sl_order_type:2`), first-entry reference (`sl_type:1`), 2% distance and static initial price `68,600`. `sl_price_rearrangement:false` keeps the pictured static price behavior. |
| SLx | Price-trigger trailing enabled; TP-trigger and breakeven alternative disabled. Activation is 1%, indent 0.5%, step 0.25%, interpreted by Liftx's existing trailing owner and reference pricing. |
| TP | Enabled with one virtual-limit exit (`tp_order_type:3`) at `72,100`; rearrangement/grid disabled. Weight `1000000` denotes the full TP. Zero input quantity is a builder placeholder, not a request to close zero. |

All four OPEN decimal arrays and the three feature switches (`sl_enabled`, `slx_enabled`, `tp_enabled`) are required. Enabling a protection requires its applicable fields; inactive options are omitted here. Explicit initial SLx price pairs are optional: use the builder's fee-aware reference if supplying them. Do not calculate them from an assumed fill at the limit price.

A rearranged SL or TP has different intent: use `sl_price_rearrangement:true` with the chosen SL reference/distance, or `tp_price_rearrangement:true` with valid price-distance `tp_pnls`. Do not treat the pictured static prices as fixed while also enabling rearrangement. [Protections and grids](/api/protections-and-grids) covers those alternatives and TP-trigger SLx.

## Minimum shape for a market entry

For the same illustrative derivative catalog, the following is a complete market OPEN with all protections disabled. It is a **separate alternative**, not an additional command to send after the limit example.

```json
{
  "client_command_id": "btc-controller:market-example:open",
  "issued_at": 1893456000,
  "expires_at": 1893456060,
  "action": "open",
  "exchange_link_id": 17,
  "instrument_id": "BTC-USDT-SWAP",
  "request": {
    "action": 1,
    "exchange_link_id": 17,
    "instrument_id": "BTC-USDT-SWAP",
    "quantity_asset": "BTC",
    "position_side": 1,
    "open_order_type": 2,
    "open_prices_atomic": [
      "70000"
    ],
    "open_prices_scale": [
      0
    ],
    "open_quantities_atomic": [
      "1"
    ],
    "open_quantities_scale": [
      3
    ],
    "order_grid_enabled": false,
    "margin_mode": 1,
    "leverage": 2,
    "sl_enabled": false,
    "slx_enabled": false,
    "tp_enabled": false
  }
}
```
A market order still supplies one positive, tick-quantized reference price and quantity row. There is no zero-price sentinel. The reference price supports sizing and validation; it does not constrain the eventual fill. The example retains `70,000` only to demonstrate the format. Use a current reviewed builder/catalog reference for a real command.

For spot, select its own catalog ID (for example `BTC-USDT` only when your catalog actually returns it), include the eligible `trading_currency`, and omit derivative-only margin/leverage fields. A `quantity_asset:"BTC"` quantity of `"1"` at scale `3` is `0.001 BTC`; a quote-asset input would have different units. Account for fees and the minimum orderable exit size: the smallest permitted gross spot entry does not necessarily leave a fee-reduced amount large enough to close in a separate order.

For an OPEN grid, set `order_grid_enabled:true`, supply `num_open_orders` and aligned price/quantity rows. That remains one Liftx position lifecycle. Independently submitted OPEN commands create separate lifecycles even when a venue nets their exposure together.

## Submit and follow the result

```sh
curl --fail-with-body \
  -H "Authorization: Bearer ${LIFTX_API_KEY}" \
  -H 'Content-Type: application/json' \
  --data-binary @reviewed-open.json \
  https://api.liftx.io/v1/commands
```

New acceptance returns HTTP `202`:

```json
{
  "id": "11111111-1111-4111-8111-111111111111",
  "client_command_id": "btc-controller:cycle-001:open",
  "action": "open",
  "state": "accepted",
  "position_id": "11111111-1111-4111-8111-111111111111",
  "error_code": null,
  "created_at": 1893456000,
  "updated_at": 1893456000
}
```
A later receipt read can return HTTP `200`:

```json
{
  "id": "11111111-1111-4111-8111-111111111111",
  "client_command_id": "btc-controller:cycle-001:open",
  "action": "open",
  "state": "handed_off",
  "position_id": "11111111-1111-4111-8111-111111111111",
  "error_code": null,
  "created_at": 1893456000,
  "updated_at": 1893456001
}
```
`handed_off` establishes the correlated durable OPEN creation. It does not certify that the exchange accepted an order or that it filled. Read the exact position and its orders, allocations and protections using [position state](/api/position-state). An accepted ID can precede the position's first publication.

## Rejection and ambiguous outcomes

An inner instrument that differs from the envelope produces HTTP `400`:

```json
{
  "success": false,
  "error": {
    "code": "SCOPE_MISMATCH",
    "message": "Position request must match command scope"
  }
}
```
A catalog/account or trading-readiness rejection can instead occur **after** acceptance and appear on the receipt. Keep following the accepted UUID. If the HTTP response is lost, resend the exact saved command; creating a new client ID can open another position.

Leverage preflight can perform exchange I/O before a later admission failure. A command is not one atomic exchange/database transaction. `operator_required` preserves unresolved effects and blocks blind replay. Do not infer that a failed request left every account setting unchanged.

A short uses `position_side:2` only where supported. The API does not translate a generic sell signal into either short or close: choose `open` with the intended direction or [terminate](/api/terminate-positions) an existing position explicitly. TradingView uses the same underlying request and trading owners through its [guided or advanced setup](/integrations/tradingview/overview).
