Advanced senders use the same durable command model as the API. The TradingView envelope adds its restricted `token` and setup-bound source information. Send exactly one `command` or `alert`; they are distinct authoring formats for the same trading owners.

<Warning>
Examples use synthetic identifiers, an invalid key and fixed illustrative timestamps. They describe shape and must not be replayed as current events. `BTC-USDT-SWAP` is an illustrative exact linear catalog ID, not a universal symbol syntax; use the value generated for your selected account. Generate live times and use the private values from Liftx. Execution remains gated by [availability](/availability).
</Warning>

## Guided OPEN

```json
{
  "token": "REPLACE_WITH_RESTRICTED_TRADINGVIEW_KEY",
  "command": {
    "client_command_id": "example-strategy:cycle-47:open",
    "issued_at": 1893456000,
    "expires_at": 1893456060,
    "action": "open",
    "target": "position",
    "exchange_link_id": 17,
    "instrument_id": "BTC-USDT-SWAP",
    "client_position_id": "example-strategy:cycle-47",
    "position_started_at": 1893456000,
    "source_instance_id": "11111111-1111-4111-8111-111111111111",
    "sequence": 101,
    "binding_revision": 1
  }
}
```

Guided OPEN omits `request` because Liftx saved it during setup. Advanced OPEN adds the complete canonical request below. Do not send a second order model based on TradingView's broker-emulator fields.

## Exact termination

Reuse the lifecycle reference and immutable start, increment the sequence, allocate a new command ID and omit `request`:

```json
{
  "token": "REPLACE_WITH_RESTRICTED_TRADINGVIEW_KEY",
  "command": {
    "client_command_id": "example-strategy:cycle-47:terminate",
    "issued_at": 1893456120,
    "expires_at": 1893456180,
    "action": "terminate",
    "target": "position",
    "exchange_link_id": 17,
    "instrument_id": "BTC-USDT-SWAP",
    "client_position_id": "example-strategy:cycle-47",
    "position_started_at": 1893456000,
    "source_instance_id": "11111111-1111-4111-8111-111111111111",
    "sequence": 103,
    "binding_revision": 1
  }
}
```

For a strategy group, change `target` to `strategy` and omit both `client_position_id` and `position_started_at`. For a market group, use `market` only with its explicit permission. Group commands also omit `request`. See [frozen group membership](/integrations/tradingview/targets-and-lifecycles).

## Modification: full current state, one exact position

Advanced modify requires modify scope, the exact lifecycle reference, a fresh intent ID and sequence, and a complete canonical `request`. If supplied, outer `expected_revision` must match the current owner revision. Direct API modification requires that revision.

The safe preparation sequence is:

1. An API controller reads [get-for-modification and current position state](/api/modify-positions).
2. It maps that position publication into the complete `PositionRequest`, retaining current rows, slot identities and immutable fields. The read response is not itself a ready-to-submit request.
3. It changes only the intended supported protection configuration. TradingView protection-only modification must preserve every OPEN row, including exact slot identities; same-size replacements still count as OPEN changes.
4. It emits an exact-position `modify` intent with the resulting complete request and, preferably, the observed revision.
5. It follows the receipt and resulting state. A conflict requires a fresh read and a deliberate new intent; an uncertain outcome requires review, not whole-request replay.

Pine cannot perform step 1 or consume execution results. Therefore the supplied examples do not schedule automatic modify calls. A historical OPEN JSON is unsafe after fills, manual edits or slot-generation changes. Use the direct API for OPEN-order changes. Never broadcast one full modification request to a heterogeneous group of positions.

## Envelope rules

The outer `token` is required. Exactly one of `command` or the [ordinary `alert` format](/integrations/tradingview/ordinary-alerts) is required. The table below applies inside `command`. Conditional fields must match both the action and target; optional fields are omitted when inapplicable.

| Field | Presence | Contract |
| --- | --- | --- |
| `client_command_id` | Required | Nonempty, at most 256 UTF-8 bytes; unique intent within integration namespace; preserve exactly on retry; reserved `liftx-group:` prefix is unavailable |
| `issued_at` | Required | Positive integer Unix seconds; unseen identities must be within five minutes of issuance, with at most 30 seconds of future clock allowance, and still before their own deadline |
| `expires_at` | Required | Integer Unix seconds, after issuance and no more than 300 seconds later; generated helpers use 60 seconds |
| `action` | Required | `open`, `modify`, `terminate`; canonical TV aliases `cancel` and `close` normalize to termination |
| `target` | Optional; defaults to `position` | Omitted/`position` for exact commands; explicit `strategy`/`market` only for termination |
| `exchange_link_id`, `instrument_id` | Required | The setup's exact link and an instrument permitted by its allowlist; both must match the nested request when present |
| `source_instance_id`, `binding_revision` | Required | Exact configured values, not user-selected per event |
| `sequence` | Required | Positive integer source ordering, assigned once per intent |
| `client_position_id`, `position_started_at` | Conditional: exact target only; forbidden for groups | Exact lifecycle reference for position targeting; reference length 1–256 UTF-8 bytes; immutable positive start no later than issuance; absent for groups |
| `expected_revision` | Optional: exact MODIFY; forbidden for groups | Optional TV modify fence; when present must match current state |
| `request` | Conditional: Advanced OPEN / MODIFY; omit for Guided OPEN and all termination | Complete canonical position request where required; absent for termination |

Use integer Unix seconds for times and decimal coefficient strings for money. Strict decoding rejects unknown keys, duplicate keys, incorrect casing, trailing JSON, oversized bodies and invalid unions. One body is limited to 256 KiB.

The token authenticates admission and is not part of the persisted command payload. Identical retries return the original receipt; the same identity with changed content conflicts. Receipt evidence is explained in [delivery and troubleshooting](/integrations/tradingview/troubleshooting).
